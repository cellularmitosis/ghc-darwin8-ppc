## 1. The "complete bindist" packaging-bug class

v0.14.1's `unlit` fix surfaced one instance of the bug; v0.15.0
catches three more (ghc-pkg, hp2ps, hsc2hs).  The systematic
diagnostic is:

```bash
$ file external/.../bindist/.../bin/powerpc-apple-darwin8-*
```

If any binary says `Mach-O 64-bit executable arm64`, it's a host
binary copied verbatim by patch-0010's carve-out hole.  Pre-v0.15.0:

```
powerpc-apple-darwin8-ghc:        Mach-O 64-bit executable arm64
powerpc-apple-darwin8-ghc-pkg:    Mach-O 64-bit executable arm64
powerpc-apple-darwin8-hp2ps:      Mach-O 64-bit executable arm64
powerpc-apple-darwin8-hsc2hs:     Mach-O 64-bit executable arm64
powerpc-apple-darwin8-unlit:      Mach-O executable ppc       (v0.14.1 fixed this)
powerpc-apple-darwin8-ghc-iserv:  Mach-O executable ppc_7400  (v0.7.0)
```

`powerpc-apple-darwin8-ghc` is the cross-compiler driver itself —
it's *meant* to run on the host (which is why it's arm64).  Same for
the suffix-versioned `*-ghc-9.2.8` copies (they're aliases).

Post-v0.15.0 the four helper binaries (ghc-pkg, hp2ps, hsc2hs, ghc-iserv,
unlit) are all ppc.

## 2. Patch 0018 — bindist recache exec-on-host

Once patch 0010's carve-out grows to cover ghc-pkg, hadrian's
`binary-dist-dir` rule fails with:

```
_build/bindist/.../bin/powerpc-apple-darwin8-ghc-pkg:
  createProcess: exec: invalid argument (Bad file descriptor)
```

Hadrian's rendering of bash's `Bad CPU type in executable` error
when trying to run a ppc binary on arm64.  The offending call site
is `hadrian/src/Rules/BinaryDist.hs:204`:

```haskell
ghcPkgName <- programName (vanillaContext Stage1 ghcPkg)
cmd_ (bindistFilesDir -/- "bin" -/- ghcPkgName) ["recache"]
```

— invoked unconditionally to seed `lib/package.conf.d/package.cache`.

Pre-v0.15.0 this worked by accident: the bindist's ghc-pkg was the
host arm64 binary copied verbatim.  Post-v0.15.0 it's a target ppc
binary and can't be exec'd on the host.

Fix: wrap with `unless cross $ do ...`.  `install.sh` already runs
`ghc-pkg recache` on the target as part of its install sequence
(line 119 or thereabouts), so the user always gets a fresh cache
there.  The bindist ships without a `package.cache` file in cross
mode, which is fine — the first install seeds one.

Conceivably upstream-shape: any cross-build that ships a real target
ghc-pkg in its bindist hits this.  Mainline GHC's cross-builds
probably don't ship target ghc-pkg in bindists (or arrange differently);
we do, so we patch.

## 3. `ghc-pkg` finds package.conf.d via topdir

The deployed ghc-pkg at `/opt/ghc-stage2/bin/ghc-pkg` finds its
package db at `/opt/ghc-stage2/lib/package.conf.d/` without any
flags — that's the topdir convention (`$topdir = parent of binary +
../lib`).  Stage1's `_build/stage1/lib/package.conf.d/package.cache`
was rsync'd to pmacg5 by `deploy-stage2.sh` (rsync of stage1's `lib/`
which already includes the cache from the host build).

So we get a working `ghc-pkg list` from the deployed setup with no
extra work.  The cache was generated by stage0 (host) ghc-pkg at
stage1 build time, but the package.cache file format is host-neutral
within a given GHC version, so the ppc ghc-pkg reads it fine.

## 4. T6106's `:reload` semantics

T6106 tests that `:reload` re-runs a preprocessor whose output may
change between loads.  The script:

1. `:load shell.hs` — defines `shell :: String -> IO ExitCode`.
2. Defines a `:shell` user command via `:def`.
3. `:l` (no arg) — unloads everything.
4. `:shell rm -f T6106.hs` — clean slate.
5. `:shell echo "{-# OPTIONS_GHC -F -pgmF ./T6106_preproc #-}" >T6106.hs`
6. `:shell echo "module T6106 where" >>T6106.hs`
7. `:load T6106.hs` — first load.  Preproc reads T6106.hs, writes
   it back to ghc's input, **then sleeps 1 second**, then writes
   `"FAIL"` into T6106.hs (the orig).
8. `-- second one should fail:`
9. `:reload` — second load.  Now the orig says `"FAIL"`, which parse-
   errors.

Expected stderr (the error from step 9):

```
T6106.hs:1:1:
    Parse error: module header, import declaration
    or top-level declaration expected.
```

For our runner this means:
- `pre_cmd_for(T6106)` must produce a working `T6106_preproc` native
  binary.  `/opt/ghc-stage2/bin/ghc-real --make T6106_preproc -v0`
  does this in ~1-2 sec on pmacg5.
- The `threadDelay 1000000` in T6106_preproc.hs forces 1s gap between
  the two writeFiles to dodge HFS+'s 1-second mtime granularity (same
  granularity that bites T8042 + T17549).
- `../shell.hs` must be staged into the test dir (we list it as an
  explicit `../shell.hs` extras entry; `cp "$SCRIPTS_DIR/$x"
  "$dest/"` resolves the `..` and the cp basename is `shell.hs`).

The test passed first try.  No surprise — the test exists to verify
that `:reload` honors preproc output changes, and our REPL is intact
post-v0.14.2.

## 5. T19650 and the `-package-env` shape

T19650 tests `-package-env <file>` loading.  The setup writes
`my_package_env` containing the literal string `base-4.16.4.0`
(via `ghc-pkg latest base > my_package_env`).  Then `ghc --interactive
-package-env my_package_env -v1` loads it.

Surprisingly, the file format for `-package-env` doesn't have to be
the canonical "clear-package-db / global-package-db / package-id X"
shape — a bare `base-4.16.4.0` line is accepted as a package-id
to require, and the env auto-imports the global db, etc.

Expected stdout (post-filter):

```
Loaded package environment from my_package_env
```

The `-v1` flag is what causes ghc to print the "Loaded package env"
line.  Without `-v1` (or higher), the env loading is silent.

Filter regex `r'Loaded package env.*'` strips out the `-v1` chatter
that follows (lots of "starting Parser..." etc).  The test's
expected file also contains a `:set -DMAGIC` second line, but the
filter erases it.  Both stdout files are filtered identically pre-
diff.

## 6. `--filter-stdout-regex` quoting through bash

`norm_args_for(T19650)` returns the string
`--filter-stdout-regex 'Loaded package env.*'`.  When the runner
does `nargs=$(norm_args_for "$name")` and then `norm "$file" $nargs`,
bash word-splits `$nargs` on whitespace.  The single-quotes from
echo become literal characters, so naive splitting yields:

```
--filter-stdout-regex
'Loaded
package
env.*'
```

— four tokens.  Python sees `--filter-stdout-regex` followed by
`'Loaded` as the arg value, which doesn't match what we want.

Fix: `eval`-wrap the `norm` call.  `eval` re-parses the line
(including the single quotes from `$nargs`) and groups
`'Loaded package env.*'` back into one shell token.  No behaviour
change for tests whose `norm_args_for` returns empty or single-
token args.

Alternative considered: have `norm_args_for` return tokens separated
by null bytes, or use bash arrays.  `eval` is simpler and the inputs
are entirely under our control (hardcoded test names), so injection
risk is nil.

even though they're not strictly needed for T19650.  Rationale: the
fix is the same one-line carve-out edit, and they exhibit the same

routes through the cross-cc with no Haskell deps.  hsc2hs is a
Haskell program (uses `process`, `directory`, etc.) so it routes
through stage1 ghc; ~25 MB binary.
